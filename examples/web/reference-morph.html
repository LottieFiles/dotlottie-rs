Reference-layer morph — the design lives in the file

The runtime is not a design tool, so the target of an interaction shouldn't be a hand-typed matrix. Here the designer authored a null layer (REF:dock) — never rendered, but present in ThorVG's tree with its animated transform. "Dock" morphs the bell onto whatever the reference currently is; since the reference itself is animated, the docked bell keeps following it.

—

Why a null layer

ThorVG's Lottie builder skips zero-opacity layers entirely (unqueryable) and AE-hidden layers are dropped at parse — but null layers are explicitly kept: they get a named scene carrying the animated transform, render nothing, and cost nothing. That makes them the natural authoring vehicle for "where should this land" references. (A normal layer hidden at runtime with set_layer_visible(false) is the alternative when the reference must also carry opacity.)

APIs used

const R = player.get_layer_transform("REF:dock"); // sampled at current frame
const B = player.get_layer_transform("bell");     // pristine animated value

// morph matrix: at t=1 the bell's final transform equals R exactly
const M = mul(R, invert(B));
player.set_layer_transform("bell", lerp(IDENTITY, M, t));

State-machine shape

TweenToLayerReference { target, reference, duration, easing } — the SM never stores design data; it stores two layer names. Values come from the file at runtime, so designers iterate on the .lottie without touching the state machine. This is the missing piece that keeps the SM an interaction tool, not a design tool.
